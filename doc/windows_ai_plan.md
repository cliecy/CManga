# Windows AI 超分与上色接入计划

## 目标与范围

打通 Windows 上的真实本地 AI 超分和 AI 上色，同时修正参数不可细调、实际运行引擎不透明的问题。本文件是实施计划，不表示功能已经实现或通过运行验证。

交付目标：

- Windows 阅读器实际执行 ACNet / Real-ESRGAN 超分及 DeOldify 上色，而不是静默回退 v1 或保留未上色图片后显示成功。
- CPU 推理必须可用；兼容设备提供 DirectML 加速，并明确显示实际执行后端及回退原因。
- 超分区分模型原生倍率、最终输出倍率和增强强度；允许 1.3×、1.75× 等倍率，以及 0–100% 独立强度细调。
- 上色提供独立颜色强度滑块，支持 0–100% 细调，并保留现有最高 120% 的增艳范围；说明它不是配色指令或模型质量参数。
- 模型下载、本地导入、切换、删除、缓存刷新、安装包依赖全部闭环。
- 保持 Android 功能；不把 iOS、macOS、Linux 错标为支持原生 AI。
- Windows x64 为现有 CI 主线；同步处理已有 ARM64 构建入口，CPU 为基础验收，GPU 支持按实际依赖与设备探测，不把 x64 产物冒充 ARM64。

不扩展为手动涂色、提示词配色、跨页人物颜色一致性、新模型训练或其他桌面平台移植。上色输入分辨率尊重模型契约，不用修改一个常数来承诺提高模型质量。

## 技术决策

### 原生实现

采用 Windows C++ + ONNX Runtime + OpenCV，通过现有 `com.github.kiastr.venera_ssr/colorize` MethodChannel 接入。不引入 Python 子进程，不要求用户另装 Python、CUDA 或手工配置 DLL。

原因：现有两项功能已经使用该通道，OpenCV 能复用已有预处理/后处理语义；无需同时重写 Android 推理和引入第二条 Dart FFI 调用链。

Windows 新增职责清晰的少量文件：通道桥接、推理/图像处理、会话管理。只抽取两项功能确实共享的代码，不建设通用 AI 插件框架。

### 后端策略

- 用户配置：`auto`、`cpu`；`auto` 在 Windows 尝试 DirectML，在 Android 沿用已验证的平台策略。
- Windows DirectML 不可用或模型执行失败时，重试同一 AI 模型的 CPU 路径；不把 v1 算法当作 AI CPU 回退。
- 回退和最终失败必须传递至界面；失败仍可保留图片供阅读，但不得显示本页 AI 处理成功。
- DirectML 同一会话串行执行，禁用 memory pattern，使用 sequential execution。不要沿用 Dart 最大并发 2 就并发调用同一 DML session。
- 后台工作线程执行解码、推理和编码；在 Flutter 平台线程回复。窗口关闭时停止接单、正确释放任务与资源，避免悬空回调。
- 会话按模型身份、后端及固定输入尺寸复用。设置有限缓存，避免超分/上色每页反复加载，也避免多个大模型无界常驻。

DirectML 官方已进入维护模式，但仍受支持。本项目选择它是为了显式部署、现有 ONNX 模型和 Windows 10/11 兼容范围，不在本次同时引入 WinML 动态 EP 管理。锁定版本前验证模型算子、目标架构及最低系统要求。

### 通道与状态契约

保留通道名称和 `colorize` / `resetSession` 方法，增加能力与模型探测。协议变更一次性迁移 Dart 和 Android 调用方，不长期保留 `useNnapi` 和新后端参数两套接口。

- `getCapabilities`：返回支持的处理类型、可选执行后端及不可用原因。
- `getModelInfo`：验证加载，返回输入类型、通道数、空间尺寸约束及超分倍率；不根据文件名或文件大小宣称模型兼容。
- `colorize`：输入图片、模型身份/路径、处理类型、后端策略；返回 PNG 字节及实际后端、原生倍率和回退原因等必要元信息。
- 推理失败用明确错误返回；缓存命中与实际推理要区分，不能显示不存在的本次 GPU 执行。
- Android 的 `copyUri` 保留为平台文件访问能力；Windows 使用 Dart 文件流复制，禁止调用 ContentResolver。

## 阶段一：建立可运行的 Windows 推理基础

涉及 `windows/runner/`、两级 CMake 配置、Windows 构建脚本。

1. 准备 Flutter、Visual Studio C++ 工具链、Windows SDK；确认可启动当前 Windows 应用。
2. 锁定 ONNX Runtime/DirectML/OpenCV 的版本、架构、下载来源与校验值；优先裁剪 OpenCV 至 core/imgproc/imgcodecs 及必要编解码依赖。
3. 将 AI 原生实现作为独立 CMake 目标，局部处理异常设置，避免为无关 runner/plugin 修改全局编译语义。
4. 注册通道，实现能力检测、模型检查、会话释放和有界后台执行。
5. 用内置 ACNet 真实执行小图片，先证明 CPU 路径，再验证 DirectML；这是中间检查点，不是最终交付。
6. 确认 DirectML 加速组件缺失或设备不兼容时，程序仍可启动并使用 CPU，而不是在进程加载阶段因 DLL 问题退出。

阶段出口：Windows 原生程序经 Flutter 通道获得真实推理输出；依赖从构建产物目录加载，主线程不承担推理。

## 阶段二：打通 AI 超分、倍率与增强强度

涉及 `anime4k_v4_service.dart`、`anime4k_v4_model_manager.dart`、`reader_image.dart`、`appdata.dart`、超分设置页、阅读器设置页以及 Windows 引擎。

1. 实现 ACNet 单通道亮度管线和 Real-ESRGAN RGB 管线，按模型元信息选择输入布局及输出倍率。
2. 对大页采用有重叠的分块推理，处理边界填充、裁切、拼接以及奇数尺寸；对输出像素总量做可解释的内存约束，超限不擅自降低倍率。
3. 增加“最终输出倍率”：默认跟随模型；自定义 1.00× 至模型原生倍率，滑块步进 0.05×，数字输入精度 0.01×。
4. 比如 2× 模型输出后高质量缩小至 1.30×；尺寸为相对进入超分阶段原图的 `round(width × scale)` / `round(height × scale)`。不重复执行模型凑倍率，不把超过模型倍率的插值标为 AI 细节。
5. v1 保留现有 1–4× 范围，将倍率控制同样细化；不把旧 v1 倍率偷偷迁移为 v4 目标倍率。
6. 新增独立“超分强度”，范围 0–100%，步进 1%，默认 100%，支持滑块与数字输入。设置使用独立键（例如 `anime4KEnhancementStrength`），不得复用原本表示对比度的 `anime4KV4Intensity`。
7. 强度采用同尺寸残差混合：`输出 = 基础缩放图 + strength × (AI 超分图 − 基础缩放图)`。先将两张图转换至同一目标尺寸与颜色空间，在浮点线性 RGB 中混合，再编码输出；正确处理透明通道。0% 是普通高质量缩放，100% 是完整 AI 输出，50% 是二者中间结果，不改变倍率。v1 同样可将其算法增强结果与基础缩放图混合，原有 Push 参数仍独立。
8. 现有 v4 `intensity` 更名展示为高级“输出对比度”，保留旧设置值及其历史行为，不把对比度混作新增强强度。对比度只作用于 AI 分支后再参与混合，确保强度 0% 不受 AI 对比度影响。混合端点分别直接复用基础/AI 结果，避免不必要的计算或数值漂移。
9. 将模型推理输出与最终缩放/对比度/强度后处理分开缓存。只改这些参数时复用该阶段推理结果，不重复执行超分模型；没有缓存且强度为 0% 时直接输出基础缩放图，不为无效贡献运行推理。
10. 模型导入/替换/删除后更新模型身份、清理相应结果并刷新阅读器；使用能力结果替代 Android 硬编码判断。

阶段出口：Windows v4 真正执行模型；1.30×、1.75× 等目标尺寸精确；强度从 0% 到 100% 可细调且不改变尺寸；界面明确显示模型原生倍率、目标倍率、增强强度和实际后端。

## 阶段三：打通 AI 上色和强度调节

涉及 `colorization_service.dart`、`colorization_processor.dart`、上色设置页、`reader_image.dart`、Windows 引擎。

1. 完成当前产品实际使用的 DeOldify Artistic 及其兼容 int8 变体；以输入/输出类型与张量布局验证兼容性。
2. 按实际模型契约完成归一化、通道排列、输出色彩转换。现有 Android 代码存在特殊的 RGB/BGR 和亮度处理约定，应使用相同模型的参考输出核对，不能只靠“看起来有颜色”验收，也不在移植时未经验证改写画风。
3. 原生代码中虽然存在 DDColor 分支，当前 Dart 调用固定为 DeOldify。本次不宣称任意 DDColor/任意 ONNX 导入都可用；不兼容模型明确拒绝。
4. “上色强度”标注为颜色浓度，界面用百分比显示：0–120%，步进 1%，数字输入同精度，默认 100%，保存时沿用 0.00–1.20 数值及旧设置。0% 表示中性色度，100% 表示模型预测色度，120% 表示额外增艳；不改变亮度分量和图像尺寸。0% 不声称逐字节还原原图，关闭功能才是完全跳过上色。
5. 强度不参与模型推理。保留未裁剪的基础预测色度及亮度数据，调强度只做后处理，不重复运行上色模型，也不从已量化/截断的 PNG 反推色度。强度为 0% 且没有推理缓存时，直接按同一亮度约定生成中性结果，不执行无贡献的推理。
6. Windows 提供 Auto/CPU；Auto 尝试 DirectML，模型或设备不兼容则报告 CPU 回退。Android 默认上色保持现有 CPU 策略，不顺带改变未经验证的加速行为。
7. 文件存在不等于功能就绪：区分未下载、模型不兼容、后端不可用、就绪、正在处理和失败。
8. Windows 本地模型采用流式复制至临时文件，验证后替换；模型替换失败保留原可用模型。修正现有导入/恢复流程，避免旧会话或旧缓存继续生效。

阶段出口：Windows 使用真实 DeOldify 输出；调浓度有可见变化、不改图片尺寸、也不改变模型所预测的配色语义。

## 阶段四：阅读器、状态与缓存闭环

1. 保留现有“超分 → 上色”处理顺序，不在移植中悄悄改变视觉结果。
2. 缓存身份包括输入内容/上游处理版本、模型版本或内容标识、算法版本和实际影响像素的参数；不能只用 URL 和强度，否则超分变化后可能拿到旧上色结果。
3. 基础推理缓存与显示结果缓存分别失效，不无差别删除所有模型与图片缓存。重复请求共享在途结果，不因“正在处理”就把未处理图当成最终结果。
4. 开关、模型、倍率、超分强度和上色强度修改后，复用 `PaintingBinding.instance.imageCache` 与 `ComicImage.clear()` 刷新路径；拖动时更新数值，拖动结束或短暂防抖后刷新图像，旧任务不得覆盖新参数结果。纯后处理复用本阶段模型结果；若超分变化确实改变下游上色输入，则正确重新执行上色，不能为了“不重跑”复用错误输入的结果。
5. 全局设置与漫画专属设置使用现有优先级；两个入口显示同样的平台能力和参数语义。
6. AI 失败不静默变成 v1。保留图片并显示本页未完成及原因；用户主动选择 v1 时才使用传统算法。
7. 显示实际处理模式、模型和后端；能力探测可用不等于整张图全部算子都在 GPU。遇到 CPU 回退/混合执行按可验证信息表述。
8. 更新 `assets/translation.json` 的相关提示，移除已不准确的 Android-only 文案，但其他未接入平台继续明确提示不支持。

## 阶段五：发布与端到端验收

### 构建和打包

- CMake 安装规则包含 ONNX Runtime、DirectML、OpenCV 及其实际运行依赖，避免仅在开发机 PATH 下可运行。
- `.github/workflows/Windowsdart.yml` 增加确定性的依赖准备、CPU 真实模型 smoke 和产物核查；GPU 验证使用有硬件的 Windows 机器，不能以托管 CI 编译成功代替。
- 核对 `windows/build.py`、`build.iss`、`build_arm64.py`、`build_arm64.iss`：架构匹配、正确产物路径、非零错误码终止。ARM64 的依赖可用性在阶段一验证，不能最后才发现打包的是 x64。
- 在未安装 AI 开发依赖的干净 Windows 环境启动 ZIP 和安装版；内置 ACNet 开箱可用，已下载上色模型可离线使用。
- 保留既有 release 产物匹配规则；只有产物命名确实变化时才修改发布工作流，不修改无关版本号与发布策略。

| 快速翻页、切模型、关闭窗口 | UI 可响应，无无界任务堆积、崩溃或销毁后回调 |
| 干净机器、离线已备模型 | 无缺 DLL；两项 AI 真正可运行 |
| Android 回归 | 原有超分/上色和平台文件导入保持可用；共享协议无遗漏 |
| 其他未支持平台 | 不调用不存在的原生通道，不显示已就绪 |

使用真实模型及可再现样图；记录模型哈希、后端、输入/输出尺寸、耗时、峰值内存和对比图片。指标用来描述已测结果，不预先承诺所有显卡实时处理。ARM64 若缺少可执行环境，明确列为未验证，不宣称对应架构验收通过。

现有测试处理：删除依赖已经移除函数、固定文件名/体积等实现细节的失效测试；只保留或新增能防止尺寸、色彩、缓存失效和状态转换实际回归的测试。Flutter mock 通道测试不作为 Windows 原生可用的证据。最终集中执行必要的格式化、分析和受影响测试，并实际启动 Windows 应用操作设置、阅读和离线加载。

真实 smoke 通过后，更新现有 README 的支持矩阵与设置说明，移除临时脚本/产物，完成最终依赖和许可说明。

## 实施顺序与完成定义

顺序：共享原生基础与协议 → 超分/上色管线 → 阅读器与参数闭环 → 安装包及实机验收。基础稳定后两条管线可独立开发；通道协议、会话管理、阅读器共享修改指定单一集成负责人，避免并发改同一文件。

完成必须同时满足：Windows 两项真实 AI 输出、倍率及两项独立强度可细调、可解释的 CPU/GPU 状态、模型生命周期与缓存正确、安装包可独立运行、Android 无回归。只去掉平台判断、只构建通过、只得到 mock 返回或只跑通 CPU 中间检查点，都不算计划交付完成。
